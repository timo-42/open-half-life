# M9 scripted-input scenario: a spawn-to-exit progression walk in Power
# Up.
#
# Project-authored; no bytes here come from any game installation (see
# docs/CLEAN_ROOM.md). Run against "c2a1" (Power Up, per
# ohl_campaign::CHAPTERS's own cited table) by xtask/src/combat_smoke.rs,
# with `--follow-level-change` so a `trigger_changelevel` this walk
# reaches is actually followed rather than only logged as "not followed".
#
# Route, in words only (no entity name, path or coordinate from any
# payload): from the player's spawn point, advance forward through a long
# sequence of turns, passing near a monster along the way (a source of
# damage to it, not a route failure), until a level change fires; then
# wait out the transition. No door needs opening on this route.
#
# Expected fixed log lines, asserted by the harness rather than parsed
# from this file:
#   present: "Scripted input loaded.", "Scripted input finished.",
#            "The player moved from the spawn point.",
#            "A monster took damage.",
#            "A level change was followed."
#   absent:  every other fixed line, including "The player is inside
#            solid geometry." (this scenario's own regression guard for
#            the PR #91 class of bug) and "The player opened a door."
#            (no door is opened on this route)
# Re-authored for M9.11 (docs/FORMAT_SOURCES.md item 33,
# docs/MILESTONES.md M9.11): `func_monsterclip` is no longer solid to the
# player, and this map carries 29 `func_monsterclip` entities, so the
# route this file previously replayed (flown before that fix, against a
# collision model that incorrectly treated `func_monsterclip` as solid to
# the player too) no longer reaches its `trigger_changelevel` under the
# corrected engine. This file's steps are a *new* route, authored fresh
# against the corrected engine using an earlier investigation's own
# two-`Game` technique (recorded in local notes, not part of the
# repository): a "planning" `Game` runs a breadth-first walk with
# parent pointers over its live collision model (mirroring
# `ohl_engine::reachability`'s own step-up/across/drop shape, `CELL_SIZE`/
# `STEP_UP`/`DROP` constants and all — that module's own `walk` is
# private, so the planner reimplements it) from the player's own spawn
# point until a `trigger_changelevel` volume's bounds are reached, giving
# a waypoint path (no door needed: `--reachability-report` already found
# the trigger reachable at round 0, ~930 units from spawn, unchanged from
# before the fix). A **second, freshly reloaded** `Game` then flies an
# autopilot along that path exactly as that same earlier investigation
# describes: turning by the difference between the current eye yaw (read
# from the real camera at the start, not assumed) and the bearing to the
# next waypoint, walking forward once roughly facing it. The raw per-tick
# turns below are kept one tick per line rather than merged into blocks:
# a merge-and-rescale pass was tried and tested end to end through the
# real binary, and it silently changed the outcome (the merged script no
# longer reached the level change) — the same sub-degree rounding risk
# that same earlier investigation itself already flagged for a merge that
# only combines *bit-for-bit identical* per-tick turns; this route's own
# turns are almost never identical tick to tick (the autopilot re-aims
# every tick), so merging would only ever reintroduce that risk for a
# very small, single-digit-percent line-count saving. Verified end to end
# against the real `open-half-life --script --script-log
# --follow-level-change` binary; 2 iterations against the real binary
# (the first, freshly-planned route worked; a merged variant of it did
# not and was discarded), within the 10-iteration budget.
#
